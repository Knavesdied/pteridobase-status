# Upptime check dispatcher

A Cloudflare Worker that asks GitHub to run this repo's `uptime.yml` every five
minutes, because GitHub's own cron does not.

Pteridobase [#869](https://github.com/Knavesdied/Pteridobase/issues/869).

## Why

Measured on this repo, GitHub delivered **2.0–2.9%** of the five-minute cron's
configured firings, with a longest observed gap of **271.6 min (4h 32m)**. That is the
platform's base rate rather than a misconfiguration here: Upptime's own reference
deployment manages 8.7%, and across 299 consecutive intervals there **not one was under
7.5 minutes**. GitHub's docs say scheduled events "can be delayed" and that "some
queued jobs may be dropped"; there is no SLA.

This matters because of what Upptime uniquely catches. UptimeRobot polls the same sites
every five minutes and is reliable, but its free tier is **down-only** — a site serving
HTTP 200 in 8–16 seconds is invisible to it. That is the failure Pteridobase has
actually had, on 1 and 2 September 2026. Catching it is Upptime's `maxResponseTime`
alone, so **Upptime's cadence is the detection latency for that entire class**.

## How

`src/index.js` runs on a Cloudflare cron trigger and POSTs to:

```
POST /repos/{GH_OWNER}/{GH_REPO}/actions/workflows/{GH_WORKFLOW}/dispatches
{"ref": "{GH_REF}"}
```

`uptime.yml` already declares `workflow_dispatch`, so nothing in `.github/` was
modified — which matters, because every workflow here carries "Do not edit this file
directly" and `update-template.yml` regenerates them **daily** from an unpinned
`upptime/uptime-monitor@master`. A hand-edit there has a shelf life of about a day.

**`workflow_dispatch`, not `repository_dispatch`** — though `uptime.yml` accepts both.
`repository_dispatch` is Upptime's documented path, but GitHub returns `204 No Content`
even when the `event_type` matches nothing at all, so a typo dispatches into the void
with no error to observe. #869 exists because a monitor failed silently; the endpoint
that can report its own misconfiguration was worth the extra `ref`.

**It does not perform the check itself.** It asks GitHub to run Upptime's workflow, so
the status page, history, graphs and notifications remain exactly as Upptime defines
them. A Worker that curled the sites directly would be a second, divergent
implementation of something that already works.

## Configuration

All in `wrangler.jsonc` as `vars` — none is secret, and the repo path in particular
must be editable, because [#865](https://github.com/Knavesdied/Pteridobase/issues/865)
moves this repo to an organisation and `GH_OWNER` changes with it.

| Var | Purpose |
|---|---|
| `GH_OWNER` / `GH_REPO` | Repo path. **Change both when #865 lands.** |
| `GH_WORKFLOW` | Workflow *filename* — the dispatches endpoint takes the file, not the name |
| `GH_REF` | Branch to run against; a nonexistent one returns 422 |
| `STALE_AFTER_MIN` | Log an error if no run of `GH_WORKFLOW` is newer than this |

One secret, set outside version control:

```sh
npx wrangler secret put GH_TOKEN
```

A **fine-grained GitHub PAT**, repository access limited to this repo, permission
**Actions: write** — that and nothing else. (`repository_dispatch` would have needed
`Contents: write` instead, a broader grant, which is a secondary reason for the choice
above.)

## Commands

```sh
npm install            # first time
npm run deploy         # wrangler deploy
npm run tail           # live logs
npm run dev            # local; hit /__scheduled to fire the cron handler
```

Wrangler is this project's **own** devDependency. Do not run the copy in a sibling
project's `node_modules` — monitoring must not depend on an unrelated project's
dependency tree.

## Two things that will look like bugs and are not

**1. Some ticks produce no run.** All eight Upptime workflows share **one** concurrency
group with `cancel-in-progress: false`, and GitHub keeps only **one pending run per
group** — surplus dispatches are *discarded*, not queued. Uptime CI finishes in 14–15 s
so there is normally slack, but the daily workflows (00:00, 01:00, 03:00, 23:00 UTC)
will eat a check when they collide. Fixing this means changing generated workflow
files, which the template updater reverts; it belongs upstream.

**2. GitHub's `*/5` cron is still in `uptime.yml`, and that is deliberate.** It costs
nothing because it barely fires, and it is free redundancy if this Worker ever stops.
Removing it would mean adding a `workflowSchedule` block to `.upptimerc.yml`, which
triggers a full regeneration of all eight workflows from unpinned `@master` — a real
blast radius for a cosmetic tidy.

## Verifying it actually works

Read the **runs API**, never the commit log. Upptime commits to `main` only on a status
*transition*, so an all-up check leaves no trace and any coverage claim derived from
`git log` is wrong.

```sh
gh api "repos/Knavesdied/pteridobase-status/actions/workflows/uptime.yml/runs?per_page=100" \
  --jq '[.workflow_runs[] | select(.event=="workflow_dispatch")] | length'
```

Assert the **source** as well as the count: runs must carry `event=workflow_dispatch`.
A healthy-looking cadence achieved by someone pushing commits is exactly the artefact
that invalidated the first analysis in #869 — pushes to `.upptimerc.yml` trigger
`setup.yml`, which performs a full check as a side effect.
